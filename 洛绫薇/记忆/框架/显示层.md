## 一、定位

- **显示层 = 只读呈现层**：把治理 / 运行 / 审计 / 归档四层的数据**显示给人看**，并把人的操作**交给运行层**，自己不存真相。
- **不存数据、不写回、不判事**：UI 只消费各层数据，不反向写业务真相。
- **五层闭环**：治理（定）→ 运行（做）→ 审计（查）→ 归档（留）→ **显示（见）**。

## 三、职责与边界

**管（显示层的事）**：
- 样式 / 布局 / 主题 / 密度 / 面板与入口的开关；
- 场景卡、简报、记忆注入等**提示的显示口径**；
- 显示性能（首屏、渲染负载）与显示相关的配置治理；
- 与 UI 有关的插件「装了 / 启用 / 生效 / 悬空」状态对账。

**不管（越界即错）**：
- 不改 `法则` / `规则` / 第二法则 / 记忆等治理层内容；
- 不把业务真相（会话、任务、客户数据）存进 UI；
- 不改引擎源码、不改不可动节点（见 `框架/场景/底层改造/底层改造清单.md`）；
- 不替主人做审美 / 体验取舍决定（皮肤、密度、布局偏好属主人）。

## 四、管理流程（显示层四步）

```
① 盘点 → ② 变更（先备份）→ ③ 验证 → ④ 回执归档
```

1. **盘点**：节点四问（装了 / 启用 / 生效 / 悬空），证据落 `D:\dsh\archives\display-layer\<日期>-盘点.md`。
2. **变更**：先快照（`D:\dsh\archives\display-layer\backup-<时间戳>\` 或 `底层回滚/snapshot.ps1`）→ 改 → 解析校验 → 记录是否需重启。
3. **验证**：
   - 配置层：JSON / YAML 解析通过；`bundles ↔ dependencies ↔ node_modules` 三方一致；
   - 生效层：宿主 pid 启动时刻 vs 文件 mtime（早于改动 = **需重启才生效**，必须标注）；
   - 渲染层：有浏览器控制手段才说「已看到」；没有就按 `创建DSH插件指南.md` 口径——「安装与注册已验证，渲染未在页面确认」。
4. **回执归档**：任务看板「完成回执」→ 通知来源 → `框架/archive/` 交接 → `tools/对账.ps1`。

## 五、优化准则

1. **先稳后靓**：不为观感牺牲稳定；任何改动可回退。
2. **默认优先**：官方默认配置能用就不改；个性化项（皮肤 / 密度 / 布局）单独列给主人拍板。
3. **可量化**：性能优化要给「改前 / 改后」证据（配置值、渲染项开关），不空说「更快了」。
4. **只动显示**：显示层优化不碰数据链路、不碰记忆插件的行为逻辑。
5. **诚实口径**：「装了」≠「启用」≠「生效」≠「看见了」，四个词不混用。
