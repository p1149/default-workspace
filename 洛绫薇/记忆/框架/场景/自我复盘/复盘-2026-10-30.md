## 四、结构性发现（不是单点失误，是机制问题）

1. **自动化组件天然高风险**：轮转（空转）、看门狗（误触发 + 权限）、心跳（已关省 token）、定时成长归纳（23:55）。这类组件必须三件套：**默认关 / 可观测（日志或状态文件）/ 可一键停**。
2. **同一事实散落五处**：`记忆.md`、`任务看板.md`、`健康摘要.md`、`会话索引.md`、`archive/`——今天四处对不上，说明缺「单一事实源 + 对账」。建议：**每轮收尾对账**（3 分钟固定动作）。
3. **归档索引是自动生成的，但今天没人跑**——INDEX 停在 15:14。要么改「每轮自动跑」，要么明确「交接写完顺手跑」。
4. **术语口径需要词表**：命令台（角色）/ 任务看板（场景）/ 场景（绑定会话）/ 分身（分叉）——今天「命令台」冲突就是口径不统一。
5. **时间 / 命名纪律**：归档文件名应严格用**实际写盘时刻**，避免「内容写 16:30、文件 16:18 写」这类错位。

## 五、沉淀的教训（建议进画像 / 记忆）

1. **配置改动 ≠ 生效**：改 profile / 插件配置后，核对宿主进程启动时刻早于改动。
2. **报错先看环境**：ACL / 沙箱类报错先查进程完整性级别（是否提升），再查权限 ACE。
3. **乱码先验字节**：终端乱码不等于文件损坏，先用 `read` / `node` 复核。
4. **脚本 BOM**：PS 5.1 的 `.ps1` 必须 UTF-8 BOM；JSON 配置写回必须无 BOM。
5. **机制先最小**：自动化组件默认不装，先跑通手动闭环再谈自动化。
6. **共享层要对账**：记忆 / 看板 / 健康 / 索引 / 归档，每轮收尾对一遍。
7. **文件大小异常先看 mtime 与增长**：0 字节 ≠ 假文件，先查是否正在被写（进程 / mtime / 大小变化），再下结论；大文件搬运后要校验完整性（zip / SHA256）。
